# Интеграция вашего сервиса — приём пользователей getatom

Всё, что нужно реализовать на вашей стороне, — один GET-эндпоинт. Рабочий пример на Node.js лежит в [examples/vendor-node/](../examples/vendor-node/) — его можно запустить локально и пройти весь цикл без доступа к getatom.

Хост сервиса может быть любым (поддомен вроде `crm.getatom.ru` или ваш собственный домен) — `aud` и адрес эндпоинта задаются конфигурацией на стороне getatom. В примерах ниже используется `crm.getatom.ru`.

## Один эндпоинт: `GET /sso?token=<jwt>`

Порядок обработки запроса:

1. **Достать токен** из query-параметра `token`. Нет токена → редирект на `https://getatom.ru/api/sso/crm` (getatom выпустит новый).
2. **Проверить подпись** по JWKS `https://getatom.ru/.well-known/jwks.json`:
   - ключ выбирается по `kid` из header;
   - допустим только алгоритм `RS256` — токены с любым другим (`none`, `HS256`, …) отклоняются до проверки подписи;
   - JWKS кэшируйте (~10 минут), при неизвестном `kid` перечитайте один раз.
3. **Проверить claims**:
   - `iss === "https://getatom.ru"`;
   - `aud === "crm.getatom.ru"` (хост вашего сервиса);
   - `exp` не истёк, `iat` не в будущем — допуск по времени не более 30 секунд.
4. **Погасить `jti`**: сохранить его (Redis/БД/память с TTL) до `exp + 30с`. Повторный токен с тем же `jti` → отказ. Так перехваченная или переоткрытая из истории ссылка становится бесполезной.
5. **Find-or-create пользователя** по `sub` — это стабильный ID пользователя getatom для вашего сервиса. `name` используйте только для отображения.
6. **Создать свою сессию**: собственная кука с флагами `Secure; HttpOnly; SameSite=Lax`, host-only (без атрибута `Domain=`).
7. **Сразу сделать redirect** на страницу приложения (например `/`), чтобы токен исчез из адресной строки, истории и Referer.

## Кнопка «Войти через getatom» на вашем лендинге

Это просто ссылка:

```html
<a href="https://getatom.ru/api/sso/crm">Войти через getatom</a>
```

Если пользователь уже залогинен в getatom — он мгновенно вернётся к вам с токеном. Если нет — увидит вход getatom и после логина автоматически продолжит тот же поток. Никаких параметров передавать не нужно: адрес возврата зафиксирован в конфигурации getatom.

## Обработка ошибок

| Ситуация | Действие |
|---|---|
| Токен истёк / нет токена | `302 → https://getatom.ru/api/sso/crm?retry=1`. Если запрос уже пришёл с `retry=1` и снова невалиден — покажите страницу ошибки, без нового редиректа (защита от петли). |
| Невалидная подпись / `iss` / `aud` | `403` + страница ошибки. Не редиректьте: это не «протухло», а неверная конфигурация или подделка. |
| Повторный `jti` | `403`, зафиксируйте в логах. |

## Несколько правил безопасности

Они короткие, но важные — без них протокол теряет свои гарантии:

- **Не логируйте значение токена** — маскируйте query-параметр `token` в access-логах и APM.
- **Куки — только host-only** (без `Domain=`), чтобы ваша сессия не пересекалась с другими поддоменами.
- **`sub` — единственный идентификатор пользователя.** Не привязывайтесь к `name` и не запрашивайте у пользователей email/телефон «для входа» — вход всегда через getatom.
- **Не открывайте `/sso` в iframe** (`X-Frame-Options: DENY` на этом маршруте).

## Выход (logout)

Сессии независимые: logout в вашем сервисе гасит только вашу куку, разлогин в getatom вашу сессию не завершает. Рекомендуемое время жизни вашей сессии — до 24 часов: дальше пользователь просто снова пройдёт бесшовный `/sso` (для залогиненного в getatom это незаметно).

## Чек-лист готовности

- [ ] `GET /sso?token=` реализован, проверки из шагов 2–4 включены
- [ ] Редирект после логина убирает токен из URL
- [ ] Повторная подача того же токена отклоняется (`jti`)
- [ ] Кука сессии: `Secure; HttpOnly; SameSite=Lax`, host-only
- [ ] `token` маскируется в логах
- [ ] Страница ошибки без редирект-петли
- [ ] Прогнано против мок-issuer'а из [examples/vendor-node/](../examples/vendor-node/)

Дальше пришлите нам хост сервиса и URL `/sso`-эндпоинта — мы включим сервис в конфиг, и можно проверять живой поток.
