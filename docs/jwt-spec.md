# Формат SSO-токена

Токен — компактный JWS (JWT), подписанный **RS256**. Передаётся один раз в query-параметре `token` при редиректе на ваш `/sso`-эндпоинт (хост сервиса может быть любым — поддомен getatom или ваш собственный домен, он задаётся конфигурацией).

## Header

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2026-07-a"
}
```

- `alg` — всегда `RS256`. Партнёр обязан **отклонять** любой другой алгоритм (в т.ч. `none`, `HS256`).
- `kid` — идентификатор ключа из JWKS. Позволяет getatom ротировать ключи без простоя.

## Payload (claims)

```json
{
  "iss": "https://getatom.ru",
  "aud": "crm.getatom.ru",
  "sub": "d0a1f3c4-9b2e-4f7a-8c1d-5e6f7a8b9c0d",
  "name": "Иван",
  "iat": 1720512285,
  "exp": 1720512345,
  "jti": "b1e2d3c4-a5f6-4708-9a0b-1c2d3e4f5a6b"
}
```

| Claim | Обязательный | Описание |
|---|---|---|
| `iss` | да | Всегда `https://getatom.ru`. Проверяется строгим сравнением. |
| `aud` | да | Хост сервиса-получателя (например `crm.getatom.ru`). Партнёр принимает токен только со своим `aud`. |
| `sub` | да | **Псевдонимный** UUID пользователя, стабильный для данного сервиса. Это НЕ внутренний ID getatom — маппинг хранится только у getatom. По `sub` партнёр делает find-or-create своего пользователя. |
| `name` | нет | Отображаемое имя. Только для UI, не идентификатор. |
| `iat` | да | Время выпуска (unix seconds). |
| `exp` | да | `iat + 60`. Допустимый clock skew при проверке — не более 30 секунд. |
| `jti` | да | Уникальный UUID токена. Токен **одноразовый**: партнёр хранит использованные `jti` до `exp + skew` и отклоняет повторы. |

## Состав токена намеренно минимальный

В токене нет email, телефона и других персональных данных — идентификация строится на стабильном `sub`, имени достаточно для UI. Это осознанное решение в пользу обеих сторон: вашему сервису не приходится хранить и защищать лишние ПДн, а пользователям — передавать их ещё одному сервису.

Если для какой-то фичи объективно нужно дополнительное поле — напишите нам: обсудим и добавим в спеку явно. Полагаться на недокументированные claims не стоит — их состав не гарантирован.

## Публичные ключи (JWKS)

- URL: `https://getatom.ru/.well-known/jwks.json`
- Формат — стандартный JWK Set (RFC 7517), ключи RSA с `kid`, `use: "sig"`, `alg: "RS256"`.
- Партнёр кэширует набор ключей (рекомендуемый TTL кэша — 10 минут) и при неизвестном `kid` перечитывает JWKS один раз перед отказом.

Пример ответа:

```json
{
  "keys": [
    {
      "kty": "RSA",
      "kid": "2026-07-a",
      "use": "sig",
      "alg": "RS256",
      "n": "xGOr-H7A...",
      "e": "AQAB"
    }
  ]
}
```

## Ротация ключей

1. getatom публикует новый ключ в JWKS **рядом** со старым.
2. Через сутки начинает подписывать новым `kid`.
3. Старый ключ удаляется из JWKS ещё через сутки.

Партнёру ничего делать не нужно, если он честно резолвит ключ по `kid`.
