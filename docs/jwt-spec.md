# Формат SSO-токена

Токен — компактный JWS (JWT), подписанный **RS256**. Передаётся один раз в query-параметре `token` при редиректе на ваш `/sso`-эндпоинт (хост сервиса может быть любым — поддомен getatom или ваш собственный домен, он задаётся конфигурацией).

## Header

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2026-07-a"
}
```

- `alg` — всегда `RS256`. Партнёр обязан **отклонять** любой другой алгоритм (в т.ч. `none`, `HS256`).
- `kid` — идентификатор ключа из JWKS. Позволяет getatom ротировать ключи без простоя.

## Payload (claims)

```json
{
  "iss": "https://getatom.ru",
  "aud": "crm.getatom.ru",
  "sub": "d0a1f3c4-9b2e-4f7a-8c1d-5e6f7a8b9c0d",
  "name": "Иван Петров",
  "given_name": "Иван",
  "family_name": "Петров",
  "email": "ivan@example.com",
  "phone": "+79161234567",
  "picture": "https://getatom.ru/api/social/profile/photo/3f2a9c.jpg",
  "iat": 1720512285,
  "exp": 1720512345,
  "jti": "b1e2d3c4-a5f6-4708-9a0b-1c2d3e4f5a6b"
}
```

| Claim | Обязательный | Описание |
|---|---|---|
| `iss` | да | Всегда `https://getatom.ru`. Проверяется строгим сравнением. |
| `aud` | да | Хост сервиса-получателя (например `crm.getatom.ru`). Партнёр принимает токен только со своим `aud`. |
| `sub` | да | **Псевдонимный** UUID пользователя, стабильный для данного сервиса. Это НЕ внутренний ID getatom — маппинг хранится только у getatom. По `sub` партнёр делает find-or-create своего пользователя. |
| `email` | да* | Email пользователя, **подтверждённый** getatom (кодом из письма или OAuth-провайдером при регистрации). Можно сразу считать верифицированным. |
| `name` | нет | Полное отображаемое имя, как в профиле getatom («Иван Петров»). |
| `given_name` | нет | Имя — первое слово из `name`. |
| `family_name` | нет | Фамилия — всё после первого слова `name`. Нет, если в профиле одно слово. |
| `phone` | нет | Телефон в формате E.164 (`+79161234567`). Передаётся **только подтверждённый** (SMS/бот-код), поэтому его можно сразу считать верифицированным. Нет подтверждённого — claim отсутствует. |
| `picture` | нет | Аватар пользователя — абсолютный публичный URL (фото, загруженное в getatom, или аватар из Google/Яндекса). Загружайте его без авторизации; сохраните у себя копию, если нужна стабильность — ссылка меняется, когда пользователь обновляет фото. |
| `iat` | да | Время выпуска (unix seconds). |
| `exp` | да | `iat + 60`. Допустимый clock skew при проверке — не более 30 секунд. |
| `jti` | да | Уникальный UUID токена. Токен **одноразовый**: партнёр хранит использованные `jti` до `exp + skew` и отклоняет повторы. |

\* `email` есть у любого аккаунта getatom, зарегистрированного через почту или Google/Яндекс. Если у аккаунта почты нет, claim отсутствует — покажите пользователю понятную ошибку, а не пустую форму.

## Профиль пользователя в токене

Email, имя, фамилия, телефон и аватар передаются, чтобы вы заводили аккаунт без повторного ввода и подтверждения контактов: getatom отдаёт только проверенные значения.

- **Идентификатор — только `sub`.** Find-or-create делайте по `sub`, не по email или телефону: у каждого сервиса свой `sub`, а контакты используйте как данные профиля.
- **Обновляйте профиль при каждом входе.** Пользователь может поменять имя, телефон или фото в getatom — перезаписывайте поля значениями из свежего токена. Отсутствующий claim не означает «стереть»: оставьте последнее известное значение.
- **ФИО.** В getatom имя хранится одной строкой, `given_name`/`family_name` получены делением по первому пробелу. Для отчества отдельного поля нет — оно попадёт в `family_name`.
- **Это персональные данные.** Вы становитесь их оператором: храните и обрабатывайте по 152-ФЗ, условия закрепляются договором (DPA).

Полагаться на недокументированные claims не стоит — их состав не гарантирован. Если нужно ещё какое-то поле — напишите нам, добавим в спеку явно.

## Публичные ключи (JWKS)

- URL: `https://getatom.ru/api/public/sso/jwks.json`
- Формат — стандартный JWK Set (RFC 7517), ключи RSA с `kid`, `use: "sig"`, `alg: "RS256"`.
- Партнёр кэширует набор ключей (рекомендуемый TTL кэша — 10 минут) и при неизвестном `kid` перечитывает JWKS один раз перед отказом.

Пример ответа:

```json
{
  "keys": [
    {
      "kty": "RSA",
      "kid": "2026-07-a",
      "use": "sig",
      "alg": "RS256",
      "n": "xGOr-H7A...",
      "e": "AQAB"
    }
  ]
}
```

## Ротация ключей

1. getatom публикует новый ключ в JWKS **рядом** со старым.
2. Через сутки начинает подписывать новым `kid`.
3. Старый ключ удаляется из JWKS ещё через сутки.

Партнёру ничего делать не нужно, если он честно резолвит ключ по `kid`.
